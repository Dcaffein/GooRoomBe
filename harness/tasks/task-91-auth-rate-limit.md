# Task-91: 인증 엔드포인트 레이트 리밋 도입

## 배경

### 현재 상태: 인증 관련 남용 방어가 전혀 없다

코드베이스 전체를 확인한 결과 아래가 **모두 부재**한다.

- 레이트 리밋 라이브러리 (`bucket4j`, `resilience4j` 등 — `build.gradle`에 의존성 없음)
- 로그인 실패 횟수 추적 / 계정 잠금 (`LoginAttempt`, `failedAttempt` 류 코드 없음)
- CAPTCHA

Redis(`spring-boot-starter-data-redis`)는 이미 도입되어 캐싱·ShedLock·인증 토큰 저장에 쓰이고 있다.

### 이것이 증폭시키는 문제들

**1. 크리덴셜 스터핑 / 계정 열거**

`POST /api/auth/tokens`는 무제한 반복 가능하며 DB에 흔적을 남기지 않는다.
task-90에서 응답을 401로 통일해도 **시도 자체를 막지는 못한다.**

**2. 타이밍 side-channel**

`LoginService:44`에서 미가입 이메일은 `:50`의 BCrypt 검증을 타지 않고 즉시 반환된다.
응답 시간이 100ms 이상 차이나므로, 응답 본문이 동일해도 가입 여부를 판별할 수 있다.
레이트 리밋이 없으면 통계적 측정을 위한 반복 요청도 자유롭다.

**3. 메일 발송 남용 — 오늘 이미 열려 있다 (task-91의 최우선 근거)**

> 이전 판에는 "task-90 전환이 이 표면을 새로 만든다"고 적혀 있었으나 **사실이 아니다.**
> 아래가 교정된 서술이다.

`VerificationService:28`이 미가입 이메일을 거르므로 `POST /api/auth/verifications` 단독으로는
임의 주소에 발송할 수 없다. 그러나 그 관문은 **요청 한 번으로 풀린다.**

| # | 요청 | 결과 |
|---|---|---|
| 1 | `POST /api/auth/users` (임의 이메일) | `PENDING` User + 미인증 LOCAL Auth 생성 → 관문 통과 조건 충족 |
| 2 | `POST /api/auth/verifications` **× N회** | `VerificationService:43`이 매번 발송. `:38`이 토큰은 덮어쓰지만 **발송은 매번 실행** |

둘 다 공개 엔드포인트이고 레이트 리밋이 없다. 즉 **2회 요청으로 임의 주소에 무제한 발송이
가능하며, 이는 현재 코드에서 이미 성립한다.**

- 피해자 주소로 무한정 메일을 발송하는 괴롭힘
- **SMTP 계정(Gmail 앱 비밀번호) 발송량 초과로 인한 차단 → 전체 가입 플로우 중단.**
  이것이 이 프로젝트에서 가장 현실적인 운영 장애다. 공격이 아니라 실수나 봇 트래픽으로도 발생한다.

참고: `POST /api/auth/users`는 메일을 보내지 않는다(`SignupService`에 `emailPort` 미주입).
발송 지점은 `VerificationService:43` 한 곳뿐이다.

**4. 저장소 용량 — task-90 전환 후 증폭된다**

현재는 이메일 기준 dedup이 걸려 있어 같은 이메일로 N번 요청해도 User 1행, Auth 1행,
토큰 1개만 남는다(`SignupService:28`, `VerificationService:38`). 따라서 **저장소 증가는
고유 이메일 수에 비례**하며, `AccountCleanupService`가 24시간마다 정리한다.

task-90(사전 인증 C-2)으로 전환하면 접수 레코드가 **토큰 단위**가 되어 이 dedup이 사라진다.
같은 이메일 N회 요청 = 레코드 N개다. C-2는 자격증명을 담지 않아 건당 크기는 작아지지만,
**증가가 요청 수에 비례하게 되는 것이 본질적 변화**다.

TTL은 이 경우 용량 방어책이 되지 못한다. 공격이 TTL 창 안에서 완결되므로 TTL을 줄여도
정상 트래픽 상주량만 줄어들 뿐이다. **용량 방어의 실질적 수단은 레이트 리밋이다.**

---

## Objective

인증 관련 공개 엔드포인트에 남용 방어를 도입한다.

- **메일 발송 트리거 남용 차단 → SMTP 쿼터 소진으로 인한 가입 플로우 전면 중단 방지.**
  현재 코드에서 이미 성립하는 문제이므로 우선순위가 가장 높다.
- 크리덴셜 스터핑 / 계정 열거 시도의 반복 횟수를 제한
- 타이밍 측정을 위한 대량 반복 억제
- task-90 전환 후 dedup 소멸로 발생하는 저장소 증가 억제

---

## Decision

- **Redis 기반으로 구현한다.** 이미 도입되어 있으며 다중 인스턴스 환경에서도 일관되게 동작한다.
  새 인프라를 추가하지 않는다.
- **task-90과의 배포 순서에 하드 의존은 없다.** 이전 판의 "task-90보다 먼저 또는 함께
  배포한다"는 철회한다 — 근거였던 "task-90이 메일 발송 표면을 새로 만든다"가 사실이 아니었다
  (배경 3 참조). 권장 순서는 **task-90 → task-91**이다.

  다만 task-90 전환 시 ① 메일 발송에 필요한 요청이 2회에서 1회로 줄고 ② 이메일 기준 dedup이
  사라지므로, **두 작업 사이의 간격은 짧게 유지한다.**

## Open Question

1. **적용 대상 엔드포인트** — 최소한 아래가 후보다.
   | 엔드포인트 | 남용 시 영향 |
   |---|---|
   | `POST /api/auth/tokens` (로그인) | 크리덴셜 스터핑, 계정 열거, 타이밍 측정 |
   | `POST /api/auth/users` (회원가입) | **현재**: 임의 이메일을 PENDING 등록해 아래 관문을 여는 진입점. **task-90 후**: 직접 메일 발송 + 저장소 고갈 |
   | `POST /api/auth/verifications` (인증메일) | 메일 발송 남용 (실제 발송 지점) |
   | `GET /api/v1/users/search?email=` | 인증된 사용자에 의한 회원 명단 수집 |

2. **제한 키 기준** — IP 단위 / 이메일 단위 / 둘의 조합.
   IP 단위만으로는 분산 공격에 약하고, 이메일 단위만으로는 여러 이메일을 훑는 열거를 못 막는다.
   `server.forward-headers-strategy: native`가 설정되어 있으므로 프록시 뒤 실제 IP 확보 방식 확인 필요.

3. **임계값과 창 크기** — 정상 사용자의 오타 재시도를 막지 않으면서 자동화를 억제하는 값.
   엔드포인트별로 다르게 잡아야 한다(로그인은 관대하게, 메일 발송은 엄격하게).

4. **초과 시 응답** — 429 Too Many Requests + `Retry-After` 헤더가 표준이나,
   429 자체가 "이 이메일에 시도가 집중되고 있다"는 신호가 될 수 있어 키 기준에 따라 검토 필요.

5. **구현 방식** — 필터/인터셉터 vs 어노테이션 기반 AOP.
   기존 `JwtAuthenticationFilter`와의 순서 관계 확인 필요.

6. **계정 잠금(lockout) 도입 여부** — 레이트 리밋과 별개 정책이다.
   잠금은 정상 사용자를 대상으로 한 서비스 거부(공격자가 피해자 계정을 일부러 잠그는) 위험이 있어
   신중해야 한다. 이번 범위에 포함할지 판단 필요.

7. **타이밍 대응 동시 처리 여부** — 미가입 이메일에도 더미 해시로 BCrypt를 한 번 태워
   응답 시간을 맞추는 방식. 레이트 리밋이 들어오면 측정 난이도가 크게 올라가므로
   추가 구현이 필요한지 함께 판단한다.
