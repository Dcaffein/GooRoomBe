# Task-90: 로컬 회원가입 사전 인증 전환 및 로그인 응답 정규화

## Background

### 문제 1: 계정 선점 탈취

`Auth.overwritePassword()`(`Auth.java:46-53`)의 가드는 `verified` 하나뿐이고,
`SignupService.signup()`은 같은 이메일 재요청 시 새 행을 만들지 않고 **기존 행을 변경**한다.

| # | 행위자 | 동작 | 결과 |
|---|---|---|---|
| 1 | 피해자 | 회원가입 → 인증메일 요청 | `PENDING` User + `Auth(victimPw, verified=false)` |
| 2 | **공격자** | 같은 이메일로 **회원가입 1회** | `verified=false` → 통과 → **비밀번호가 `attackerPw`로 교체** |
| 3 | 피해자 | 메일함의 링크 클릭 | `verify()` + `activate()` → ACTIVE |
| 4 | **공격자** | `attackerPw`로 로그인 | **탈취 완료** |

공격자의 관여는 `POST /api/auth/users` **한 번뿐이다.** 인증 메일을 받을 필요도, 볼 수도 없다.
**피해자가 자기 의지로 대신 인증해준다.** 공격 창은 가입 시점부터 클릭 직전까지다.

### 근본 원인

토큰이 저장하는 값은 `userId` 하나뿐이다(`EmailVerificationTokenRedisAdapter:23`).
발급 시점에 그 행에 어떤 자격증명이 있었는지는 기록되지 않는다.
링크가 증명하는 것은 "이 이메일의 주인이 클릭했다"뿐이며, **"그 행에 든 비밀번호를 제출한 사람이
그 주인이다"는 증명하지 않는다.** 서명은 진짜지만 서명이 무엇에 붙어 있는지가 보장되지 않는다.

더 위로 올라가면 원인은 하나다.

> **`users.email`이 UNIQUE이고, 가입 *요청* 순간부터 전역 신원 키가 된다.**
> 즉 **증명되기 전에 신원 키를 점유하도록 허용했다.**

`registerOAuthUser:48`의 `findByEmail`도 같은 뿌리다. 이메일 문자열이 같다는 이유만으로
증명되지 않은 로컬 계정에 증명된 구글 신원을 붙인다(암묵적 계정 병합).

### 왜 사후 인증을 유지하지 않는가

**사후 인증 자체는 틀리지 않았다. 업계 주류다.** 이 코드베이스의 실제 실수는 두 가지뿐이다.

1. `Auth.overwritePassword` — 재가입이 기존 자격증명을 변경한다
2. `registerOAuthUser:48` — 이메일 문자열 일치만으로 계정을 병합한다

그럼에도 사후 인증을 버리는 이유는, **"증명되지 않은 신원"이라는 상태를 유지하는 비용이
코드 전반에 흩어지기 때문이다.** 현재 이 상태 하나를 떠받치는 지점이 8곳이며
(가드 5개 + cleanup 클래스 3종), 그중 하나가 뚫려서 탈취가 성립한다.
앞으로 계정 연동·이메일 변경 기능이 붙을 때마다 "미인증 Auth가 있으면?"을 다시 물어야 한다.

대형 서비스가 사후 인증으로도 안전한 이유는 부가 장치가 많아서가 아니라 세 가지 구조적 규칙
때문이다 — ① 미인증 계정에 권한을 거의 주지 않음 ② 증명 안 된 이메일을 신원 키로 쓰지 않음
③ 계정 연동은 명시적·인증된 조작. 레이트 리밋·알림 메일·세션 무효화는 그러고도 남는
**잔여 위험**을 가두는 층이다. 그리고 그들이 사후 인증을 쓰는 동기는 보안이 아니라
**가입 전환율**이다. 본 프로젝트에는 그 제약이 없다.

> **사전 인증은 다른 길이 아니다. 같은 원칙("증명 전에는 신원 키가 아니다")을 가장 단순하게
> 달성하는 방법이다.** 관리 지점 8곳이 0곳이 된다.

본 프로젝트는 `activate()` 즉시 `UserActivatedEvent` → Neo4j `SocialUser` 노드 생성으로
곧바로 완전한 소셜 계정이 된다. 위 ①번(권한 축소)이 적용되어 있지 않다.

### 문제 2: 로그인 실패 응답

`LoginService.login()`의 네 실패 경로가 제각각이다.

| 관문 | 상황 | 응답 |
|---|---|---|
| `:44` | 미가입 이메일 | 404 |
| `:47` | LOCAL Auth 없음 (구글 전용) | **500** |
| `:50` | 비밀번호 불일치 | **500** |
| `:54` | 이메일 미인증 | 409 (`"not verified auth : 12"` — 내부 PK 노출) |

- **500의 원인**: `BadCredentialsException`은 Spring Security 예외라 `BusinessException` 규약 밖이고
  catch-all로 떨어진다. application 계층이 웹 프레임워크 예외를 던진 계층 위반이다.
  부수 효과로 비밀번호 오타 1회당 `log.error` + 스택트레이스가 남는다.
- **계정 열거**: 404(미가입)와 500(가입됨)이 갈려 상태코드만으로 가입 여부를 판별할 수 있다.
- **내부 PK 노출**: `GlobalExceptionHandler:28`이 `e.getMessage()`를 그대로 응답에 싣는다.
  **예외 메시지에 넣는 모든 값이 외부로 나간다.**

### 두 문제를 한 task로 묶는 이유

사전 인증 전환 시 `LoginService:53-55`의 `NotVerifiedException` 분기가 도달 불가가 되어
**`login()`을 어차피 건드리게 된다.**

---

## Objective

1. 로컬 회원가입을 **사전 인증**으로 전환한다. 이메일 소유가 증명되기 전에는 `users`/`auths`에
   행이 생성되지 않으며, **자격증명은 증명이 끝난 뒤에 입력받는다.**
2. 로컬과 OAuth를 **단일 모델**로 통일한다. 생성된 계정은 경로와 무관하게 항상 인증 완료 상태다.
3. 로그인 실패 세 경우를 **동일한 401 + 동일한 응답 본문**으로 통합하고 내부 PK 노출을 제거한다.

---

## Decision

- **자격증명은 증명 이후에 받는다.**
  `이메일 접수 → 메일 → 링크 클릭 → 그 페이지에서 비밀번호·닉네임 입력 → 계정 생성`
  자격증명을 증명보다 먼저 받아 보류 저장소에 담아두는 변형은 채택하지 않는다.
  공격자가 피해자 주소로 폼을 제출한 뒤 피해자가 요청한 적 없는 메일을 클릭하면
  `attackerPw`로 계정이 생성되어 공격이 형태만 바꿔 살아남는다.

- **불변식: 증명되기 전에는 신원 키가 아니다.**
  `users`/`auths`에 소유가 증명되지 않은 행이 존재해서는 안 된다.

- **로컬과 OAuth는 단일 모델로 통일한다.** "모든 가입 경로는 이메일 소유 증명을 선행 조건으로 하며,
  계정은 증명 이후에만 생성된다. OAuth는 구글이 증명하고, 로컬은 인증 메일이 증명한다."
  경로별 분기가 필요해지는 설계는 채택하지 않는다.

- **재가입 요청이 기존 자격증명을 변경하는 동작을 금지한다.** `Auth.overwritePassword()`는
  **삭제**한다. 가드 추가로 갈음하지 않는다 — 남겨두면 언젠가 다시 호출된다.
  `User.overwritePendingProfile()`도 같은 기준.

- **이메일 문자열 일치만으로 계정을 암묵 병합하지 않는다.** OAuth 자동 연동은 양쪽 이메일이
  모두 증명된 경우에만 허용한다. 전환 후 로컬 측은 항상 증명 완료이므로 남는 요구사항은
  **구글 `email_verified` 클레임 검증**이다.

- **로그인 실패 세 경우(미가입 / LOCAL Auth 없음 / 비밀번호 불일치)는 단일 401 + 동일 메시지.**
  실패 사유는 서버 로그(`warn`)에만 남긴다.

- **인증 실패 예외의 메시지는 생성자에서 고정한다.** 호출부가 주입할 수 있으면 경로별로 문구가
  갈려 열거가 다시 열린다.

- **회원가입 접수는 이메일 등록 여부와 무관하게 항상 201.** 구분은 응답이 아니라 **메일 내용**으로
  한다(미가입 → 가입 링크, 기가입 → "이미 가입된 계정입니다"). 응답으로는 알 수 없고
  실제 이메일 주인은 여전히 안다.

- **운영 디버깅 정보는 예외 메시지가 아니라 로그로 분리한다.** `BusinessException`의 `message`가
  곧 응답 본문이기 때문이다. `BusinessException`에 로그 전용 필드를 추가하는 방식은
  전 도메인이 상속하는 공용 클래스라 이번 범위에서 채택하지 않는다.

- **`Auth.verified`는 컬럼까지 DROP한다.** 항상 true인 플래그를 남기면 "미인증 Auth"라는 상태가
  다시 돌아온다. `ddl-auto: update`는 컬럼을 지우지 않으므로 수동 DDL이 필요하다.
  `UserStatus.PENDING`, `NotVerifiedException`, `AccountCleanup*` 4종도 함께 제거한다.
