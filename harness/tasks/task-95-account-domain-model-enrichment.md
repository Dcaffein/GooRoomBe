# Task-95: account 도메인 모델로 규칙 회수

> **task-94보다 먼저 수행한다.** 94가 비밀번호 정책과 이메일을 다시 건드리므로,
> 순서가 반대면 복제된 규칙을 나중에 합치는 작업이 된다.

## Background

`account/domain`은 다른 도메인에 비해 눈에 띄게 얇다.

| | 도메인 파일 수 | 대표 클래스 |
|---|---|---|
| `flag/domain` | 44 | `Flag` 252줄 |
| `social/domain` | 48 | `Friendship` 150줄 |
| `account/domain` | 24 | `User` 82줄, `Auth` 60줄 |

24개 중 실제 엔티티는 `User`·`Auth`·`RefreshToken`·`UserEventOutbox` 넷뿐이고 나머지는
예외·enum·리포지토리 인터페이스다.

**얇은 것 자체가 문제는 아니다.** 인증은 본질적으로 여러 애그리거트와 외부 자원(Redis·메일·JWT)을
오가는 프로토콜이라, 가입 한 번의 흐름이 어느 한 엔티티의 책임이 될 수 없다. 그 부분이 서비스에
있는 것은 옳다. **억지로 엔티티에 밀어 넣지 말 것.**

이 task가 다루는 것은 **그게 아닌데도 밖에 나가 있는 규칙들**이다. 네 건이고, 공통 증상은
"규칙에 집이 없어서 주석과 관례로 방어하고 있다"는 것이다.

## Objective

아래 네 규칙을 모델 안으로 회수한다. 서로 독립적이며 각각 작다.

### 1. 비밀번호 정책이 웹 DTO에 있다

현재 정책의 전부가 `SignupRequestDto`의 `@Pattern` 하나다. `src/main` 전체에서 이 정규식이
등장하는 파일도 그 하나뿐이다.

**task-94가 두 번째 입력 지점(비밀번호 재설정)을 만든다.** 그대로 두면 정규식이 복제되고,
두 곳이 갈리는 순간 재설정 경로로만 약한 비밀번호를 넣을 수 있게 된다.
**이 task의 가장 실질적인 근거다.**

DTO의 `@Pattern`을 없애라는 뜻은 아니다. 입력 형식 검증(400 즉시 반환)은 어댑터의 일이 맞다.
**정책의 단일 진실 공급원이 도메인에 있어야 하고**, 두 지점이 그것을 참조해야 한다.

### 1-b. 닉네임 정책도 같은 병이고, OAuth 경로는 **검증이 아예 없다**

같은 증상의 더 나쁜 사례다. 닉네임 제약이 존재하는 곳은 웹 DTO 둘뿐이다.

| 위치 | 제약 |
|---|---|
| `SignupRequestDto:17` | `@Size(min = 1, max = 20)` |
| `UserProfileUpdateRequest:8` | `@Size(min = 1, max = 20)` |
| `User.nickname` | `@Column(length = 20)` — DB 제약만 |

**OAuth 가입은 두 DTO를 모두 거치지 않는다.** `CustomOAuth2UserService:40`이
`userInfo.getName()`(구글 `name` 클레임)을 그대로 `registerOAuthUser`에 넘기고,
`User.createActive`는 검증하지 않는다.

**구글 표시 이름이 20자를 넘으면 계정 생성이 실패한다.** MySQL strict 모드(8.0 기본)에서는
`Data truncation` 오류로 **구글 로그인이 500**이 되고, strict가 꺼져 있으면 조용히 잘린다.
`"Christopher Alexander Thompson"`처럼 30자 이름은 드물지 않다.

정책이 어댑터 DTO에만 있고 **DTO를 거치지 않는 진입 경로가 존재한다**는 것이
비밀번호(1번)와 정확히 같은 구조의 문제다. 다만 비밀번호는 아직 두 번째 경로가 없고(task-94에서 생김),
닉네임은 **이미 있고 이미 깨져 있다.**

정책을 도메인으로 옮기면 세 진입점(로컬 가입·프로필 수정·OAuth)이 같은 규칙을 통과한다.
OAuth는 거부가 아니라 **잘라내기**가 맞다 — 사용자가 고칠 수 없는 값이고, 로그인을 막을 이유가 없다.

### 2. 비밀번호 해시가 엔티티 밖으로 나온다

`LoginService:62`가 `localAuth.getPassword()`를 꺼내 서비스에서 비교한다.

```java
if (!passwordHasher.matches(password, localAuth.getPassword())) {
```

`auth.matches(rawPassword, hasher)` 형태면 해시가 밖으로 나갈 이유가 없다.
`PasswordHasher`는 이미 포트이므로 도메인이 인자로 받아도 계층 위반이 아니다.

### 3. `RefreshToken.isExpired()`가 없다

task-89에서 **삭제됐다.** UTC/KST 혼동 버그가 있었고 고치는 대신 제거했으며, 만료 비교가
`LoginService`로 옮겨갔다.

**task-93(만료 행 정리 스케줄러)이 같은 비교의 세 번째 사본을 만들 참이다.**
task-93 문서가 UTC 주의를 크게 적어둔 것 자체가 증상이다 — 규칙에 집이 없어 주석으로 방어하고 있다.

복원하되 **시간 출처를 명시적으로 주입**해 원래 버그가 재발하지 않게 한다
(`isExpired(LocalDateTime now)` 또는 `Clock`). 인자 없는 오버로드를 두지 않는다 —
그게 있으면 호출자가 다시 `LocalDateTime.now()`를 쓴다.

### 4. 이메일 정규화 규칙이 어디에도 없다

`users.email`은 이 설계의 **신원 앵커**다 — 증명된 이메일이 곧 계정의 신원이므로
이 값이 흔들리면 계정 동일성 판단이 통째로 흔들린다. 그런데 `length = 50`짜리
원시 `String`이고, `account` 패키지 전체에 `toLowerCase()`·`trim()` 호출이 하나도 없다.

지금 대소문자 문제가 드러나지 않는 것은 **MySQL 기본 콜레이션이 대소문자를 구분하지 않기
때문**이지 코드가 보장해서가 아니다. **콜레이션에 대한 의존이 코드 어디에도 표현되어 있지 않다.**
DB를 바꾸거나 컬럼 콜레이션이 달라지면 조용히 깨진다.

값 객체(`Email`)로 승격해 생성 시점에 정규화한다. 진입 지점이 셋이라 한 곳만 고치면 안 된다 —
로컬 가입(`VerificationService`), OAuth(`CustomOAuth2UserService`), 로그인(`LoginService`).

## Decision

- **인증 흐름 자체를 엔티티로 옮기지 않는다.** 서비스 오케스트레이션이 맞다
- **task-94보다 먼저 수행한다**
- **닉네임 기준은 `1~20`자로 확정** (2026-08-13). 백엔드는 그대로 두고 프론트가 맞춘다.
  좁히는 선택지는 없다 — DB 컬럼이 `varchar(20)`이고, 10자로 줄이면 구글 이름이 긴 사용자의
  OAuth 가입이 막힌다. `min = 1`도 과거에 의도적으로 완화한 값이다
  (`ai/fix-nickname-min-length`: "닉네임 최소 글자 수 2 → 1로 완화")
- **OAuth 닉네임은 거부가 아니라 잘라내기.** 사용자가 고칠 수 없는 값이므로 로그인을 막지 않는다
- 항목은 독립적이므로 일부만 해도 된다. 우선순위는 **1-b > 1 > 4 > 3 > 2**
  (**1-b는 이미 깨져 있다** / 1은 task-94가 강제 / 4는 앵커라서 / 3은 task-93이 강제 / 2는 순수 개선)

## Open Question

1. **`Email` 값 객체의 적용 범위.** `User.email`만 바꿀지, 포트 시그니처(`findByEmail`)까지
   바꿀지. 후자는 변경 파일이 크게 늘고 다른 도메인의 조회 코드까지 번진다.
   **`@Embeddable`로 컬럼은 그대로 두면서 타입만 바꾸는 절충안**을 검토할 것
2. **비밀번호 정책의 표현 형태.** 도메인 상수(정규식 문자열)를 DTO가 `@Pattern`에서 참조하려면
   컴파일 타임 상수여야 한다. 값 객체(`Password`)로 갈지 정책 클래스로 갈지
3. **정규화 강도.** 소문자화·트림까지만 할지, gmail의 `.`/`+` 제거 같은 공급자별 정규화까지
   갈지. **후자는 권하지 않는다** — 공급자마다 규칙이 다르고 틀리면 서로 다른 사람의 계정이
   합쳐진다. 다만 명시적으로 "하지 않는다"고 정해둘 것

## 검증

- 비밀번호 정책이 **한 곳에만** 존재하는지 (`grep`으로 정규식 중복 0건)
- `Auth.getPassword()` 호출부가 `src/main`에 남아 있지 않은지
- `RefreshToken.isExpired()`에 **인자 없는 오버로드가 없는지**
- 대소문자·공백이 다른 이메일로 가입·로그인·OAuth 연동이 **같은 계정을 가리키는지**.
  콜레이션이 아니라 코드가 보장하는지 확인하려면 **바이너리 콜레이션 환경에서도 통과**해야 한다
- 기존 테스트 550개 회귀 없음
